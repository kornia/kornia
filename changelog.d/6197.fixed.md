`EdgeDetector.to_onnx` and `SuperResolution.to_onnx` with the pre- and post-processor export a model whose output is a list with one item per image for a batch of one image, as `ObjectDetector.to_onnx` does for per-image detections. A tuple with one item per image, which the output kind's reading tells from a fixed set of batched outputs by its length at two batch sizes, counts as such a list, as for `ObjectDetector` (#6192). Such a list comes from a post-processor that returns one, or, for `SuperResolution`, from the network itself or a pre-processor that returns a list of images, which `forward` runs one at a time. Both used to declare a dynamic batch, and the TorchScript exporter (`dynamo=False`) turned the list into one graph output per traced image: the graph returned two maps for a batch of three images, and two maps, one of them empty, for a single image. From torch 2.9 the dynamo exporter failed on such a model, and now exports it as well. A `dynamic_axes` or `dynamic_shapes` argument that makes the batch of such an export dynamic raises a `ValueError` after the export, before anything is saved. The kind of output is first read from a one-image forward pass outside the export, so a `ResizePostProcessor` subclass whose own `forward` returns a list eagerly is now exported for one image too, even if it returns a tensor under export, and a dynamic override of it raises. `EdgeDetector` with a `ResizePostProcessor` that keeps its own `forward` (under the class's own `forward`, without forward hooks), `SuperResolution` with known tensor-output networks and the builders' pre- and post-processors (with unchanged forwards), and a model that returns one tensor keep the dynamic batch. The check after the export reuses a positive list reading. A tensor reading is checked again at the actual tracing batch, so batch-dependent per-image outputs cannot silently produce a dynamic graph that drops images.
