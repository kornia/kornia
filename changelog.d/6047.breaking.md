`equalize`, `equalize3d` and `equalize_clahe` now raise `TypeCheckError` (a `TypeError`) for an integer or boolean image, with a message that names the dtype and the conversion `image.float() / 255`, as the `[0, 1]` adjustment functions do since #5983; the check is skipped under `disable_checks()`. Before, their `[0, 1]` range check let through an integer or boolean mask whose values are all 0 or 1: `equalize` and `equalize3d` returned the same result as for the floating-point mask and now raise, so convert such a mask with `.float()` first; `equalize_clahe` returned values that did not match the floating-point mask's (by up to almost 1.0 at `clip_limit=0`), and a boolean mask made it raise a raw `NotImplementedError`. A `uint8` image with values above 1 used to raise a `RuntimeError` and now raises the `TypeCheckError`, which `except RuntimeError` does not catch. Floating-point input is unchanged, and out-of-range floating-point input still raises the `RuntimeError` naming the range.
